Generated by /office-hours on 2026-09-11

## Problem Statement

`next-smart-router` generates a manifest of every route in a Next.js App Router
app and owns a matcher that replicates Next's precedence rules. Today that
knowledge is only reachable one URL at a time, inside a running dev server, via
the `<SmartRouterDevtools>` overlay.

There is no way to see the whole route space at once, and no way to answer the
question route bugs actually generate: _given this URL, which pattern wins, and
which patterns lost?_

## What Makes This Cool

Five tools already visualize Next.js routes (`next-route-visualizer`, two VS Code
extensions, `next-devtools`, the Next.js Explorer browser extension), and Vercel
has an open proposal to build a sixth into `next dev`
(vercel/next.js discussions #92304).

Every one of them renders **the folder tree**, because a folder tree only needs
`readdir`. None of them resolve a URL, because resolving requires a matcher that
replicates Next's precedence rules, and none of them have one. This library does.

So the deliverable is a **resolver**: give it a URL and it names the winning
pattern, the params, the patterns that also matched but lost and why, and which
query params would stick. Shipped first as a terminal command, then as a
standalone HTML file that works offline from disk.

The moat is resolution, not visualization.

**The headline capability:** because the tool owns both the pattern list and the
resolver, it can synthesize _witness URLs_ for a pattern and check whether the
pattern ever wins. If no witness wins, that route is **unreachable by any URL** —
dead code, with a proof URL attached. No folder-tree tool can produce that. This
makes the feature a **route linter that ships an HTML report**, so it also gets a
CI exit code.

Getting witness synthesis right is the whole game, and two successive naive
versions were wrong. The validated algorithm is below.

## Constraints

- Zero runtime dependencies. The generated HTML must be self-contained: no CDN,
  no external assets, no network.
- The core entry imports neither `react` nor `next`. Verified: no module under
  `src/core/` imports a `node:` builtin, `react`, or `next`.
- **v1 is roughly three focused days and contains no HTML at all.** The earlier
  drafts claimed "one weekend" while estimating five days and then three; the
  estimate is what it is, and the budget is restated to match rather than the
  other way round.

## Premises

1. The differentiator is URL **resolution**, not tree visualization. The tree is
   cut from v1 entirely.
2. A self-contained HTML file is the right _eventual_ artifact, but the resolver
   has standalone value first, so HTML is v1.1.
3. Inlining the matcher is acceptable only if the bundle is built from
   `src/core` at package build time and verified by the same extracted fixture
   that covers `src/core`.
4. Vercel shipping a route inspector would kill a tree viewer but not a resolver,
   and would not kill an unreachable-route linter at all.

## Scope split (binding)

- **v1 (~3 days, no HTML):** `analyzeRoutes` + `explain`, the devtools refactor,
  witness synthesis, `doctor`, the differential tests, **and the docs updates**.
- **v1.1:** browser bundle, `explore` subcommand, HTML page.
- **Cut from both:** the route tree. The document argues three times that the

## API shape

Two functions, split because their inputs have different lifetimes. Whole-set
analysis must not be recomputed on every keystroke in a URL box.

```ts
analyzeRoutes(routes: Iterable<string>, opts?: AnalyzeOptions)
  -> {
       ordered: string[],
       conflicts: RouteConflict[],
       unreachable: Array<{
         route: string,
         witnesses: Array<{ url: string, wonBy: string | null }>,
       }>,
       nextRejects?: { message: string },   // see "Using Next as a validator"
     }

explain(href: string, routes: Iterable<string>, opts?: ExplainOptions)
  -> {
       winner: { route, params, rank } | null,
       candidates: Array<{ route, rank, matched: boolean, reason?: RejectReason }>,
       nearMisses: Array<{ route, params, rank }>,
       stickyQuery: ParsedQuery,
     }
```

Definitions an implementer would otherwise have to guess:

- The parameter is **`href`, not `pathname`**. `stickyQuery` comes from
  `selectQuery`, which needs the query string; matching normalizes it away. The
  devtools already builds `href` from `pathname` plus `search` before calling
  `selectQuery`.
- **`candidates`** is every route in specificity order with a verdict, winner
  included; it does **not** mark the winner (`{matched: true}` describes the
  winner and every near miss identically) — derive it from `winner.route`.
  **`nearMisses`** is the subset that matched and lost, uncapped in core; the
  five-item cap stays in the devtools view.
- **`RejectReason`** is closed, one member per failure return in
  `matchPatternParams`: `"catch-all-not-last" | "catch-all-empty" |
"path-too-short" | "literal-mismatch" | "path-too-long"`.
- **Both functions build a `RouteState` internally** via `createRouteState(routes, opts)`.
  This matters twice: it is what makes `explain` agree with
  `matchRouteIn(createRouteState(routes), href)` (a naive
  `[...routes].sort(compareSpecificity)` would return `null` for
  `explain("/", ["/docs"])` while the oracle returns `/`), and it means
  `analyzeRoutes(...).ordered` contains a `"/"` the caller never passed —
  **which the unreachable pass must exclude from flagging.**
- **Config inputs are `basePath` and `locales` only.** `NormalizeOptions` is
  `{ basePath?, locales? }`; `normalizePath` rebuilds from `toSegments`, so `/a/`
  and `/a` normalize identically and `trailingSlash` plays no part in matching.
  It is consumed on the output side by `applyTrailingSlash`. Keep
  `--trailing-slash` only so `doctor`'s printed witness URLs round-trip through
  `buildHref`, and say that is why.
- **No circular dependency**: `explain.ts` → `create-router.ts` (for
  `validateRoutes`) → `url` / `segments` / `route-matcher` / `route-state` /
  `config`, no back edge. It does drag `createRouter` into the v1.1 browser
  bundle; `treeshake: true` is expected to drop it, and the bundle size check
  should confirm that.

## Witness synthesis (validated)

Two naive versions produced false "unreachable" reports on Next-legal route sets.
The working algorithm:

1. **Every synthesized segment comes from a fresh-token generator** — dynamic
   fillers _and_ catch-all tails alike. Freshness is checked against every static
   segment appearing anywhere in the route set, not just under the same parent.
   A hard-coded `x` collides with a static sibling named `x`; a hard-coded tail
   `a/b` collides with `/docs/a` and `/docs/a/b`.
2. **Catch-all witnesses run length 1 .. (maxRouteDepth − bodyDepth + 1)**, i.e.
   maximum witness _path_ depth is `maxRouteDepth + 1`, not `maxRouteDepth`.
   The argument, so nobody re-derives the shorter bound: a shadower of fixed
   depth `d` matches exactly one path depth and `d ≤ maxRouteDepth`, so depth
   `maxRouteDepth + 1` escapes all of them; a shadower ending in a catch-all is
   monotone in depth (with fresh tokens its literal prefix either agrees at every
   depth or at none), so if it shadows at `maxRouteDepth + 1` it shadows
   everywhere and no deeper witness helps. One extra length is exactly enough.
3. **Optional catch-alls include the zero-segment witness.** An earlier draft
   excluded it, justified by a `/files` vs `/files/[[...path]]` shape "in the
   existing test fixture" — the fixture contains `/files/[[...path]]` and **no**
   `/files`, so the justification was simply wrong. The exclusion also causes a
   false positive, because an optional catch-all can win _only_ in its zero form:
   for `['/files/[[...p]]','/files/[a]','/files/[a]/[...b]']`, `/files` resolves
   to `/files/[[...p]]` and every deeper URL goes elsewhere. And in the shape the
   exclusion imagined, the one-or-more witness already wins, so it was never
   needed.
4. Report unreachable only when **every** witness loses.

**Validation.** The algorithm above was implemented and fuzzed against this
library: 21,281 randomly generated route sets that `getSortedRoutes` accepts
(drawn from `{a, b, [x], [...s], [[...s]]}` to depth 3, sizes 2-5), with every
flagged route then checked against an exhaustive ground-truth URL search to
depth 4.

```
legal sets tested          : 21281
routes flagged unreachable : 250
  confirmed truly unreachable: 250
  FALSE POSITIVES            : 0
```

All six known counterexamples from two review rounds are clean. Port this fuzz
harness into the repo; it is the test that makes the feature trustworthy.

**Complexity:** with the corrected bound the pass is O(R²·D²) resolutions. Fine
at the 500-route budget; state it so nobody discovers it at 5000. Also define
`maxRouteDepth` for a single-pattern set.

## Differential testing against Next

`next/dist/shared/lib/router/utils/sorted-routes` exports `getSortedRoutes`,
Next's canonical implementation. Verified present in `next@14.2.35`, and none of
next 13.5 / 14 / 15 declares an `exports` map, so the deep import resolves across
the whole CI matrix at no dependency cost.

**Do not assert global ordering equality.** `compareSpecificity` compares ranks
left to right over `Math.min` length, then depth, then lexically; Next walks a
trie and emits whole subtrees. They diverge on both of the repo's own fixtures:

```
nsr : /  /workspaces  /docs/about  /workspaces/[id]  /workspaces/[id]/settings  /docs/[...slug]  /files/[[...path]]
next: /  /docs/about  /docs/[...slug]  /files/[[...path]]  /workspaces  /workspaces/[id]  /workspaces/[id]/settings
```

Three assertions, each scoped to what actually holds:

**A. Resolution equivalence.** For generated probe URLs, the first match under
`compareSpecificity` order equals the first match under `getSortedRoutes` order.
Measured: zero divergences across every set tested, with ~47% of generated sets
waived because Next threw.

Be honest about what this proves. It cannot fail, and that is structural rather
than lucky: two patterns that both match a path first differ at an index where
segment _ranks_ differ (two statics cannot both match; two same-rank dynamics
with different names make Next throw; an index route at the same specificity as
an optional catch-all makes Next throw), and at a rank difference the trie's
child order and rank comparison agree by construction. So it is a **regression
guard on `compareSpecificity` and `matchPatternParams`**, worth keeping, and it
is _not_ evidence about the displayed rank. Record the waive rate alongside the
result.

**B. Ordering equality restricted to same parent and same depth** — routes
differing only in their final segment. An earlier draft said "sharing a parent
prefix", which fails ~12% of the time (`['/b/b','/b/a/[x]']` orders differently
because the trie emits a whole subtree before the next sibling). The correct
restriction was validated exhaustively over all non-empty subsets of
`{a, b, c, [x], [...s], [[...s]]}` under five parents: **0 divergences in 235
accepted sets.**

**C. There is no "clean input implies the oracle accepts it" invariant.** Two
earlier drafts asserted one and both were wrong. `validateRoutes` returns `[]`
for `['/', '/[[...s]]']` and for `['/files','/files/[[...path]]']`, and
`getSortedRoutes` throws on both. Adding an `index-vs-optional-catch-all` error
kind and tightening "error-free" to "zero conflicts at any level" still fails:
measured over 119,807 sets, **68,935 of 107,906 conflict-free sets still throw**,
because `validateRoutes` checks slug-name consistency only among siblings under
one parent while Next's trie checks every position tree-wide
(`['/[x]/[y]','/[y]/b/[y]']` collides at index 0 and `validateRoutes` cannot see
it). Closing that gap means reimplementing Next's validator, which is not this
feature.

So: **skip sets the oracle rejects, and narrow the catch.** Match the error text
against the known Next messages and rethrow anything else, so a harness bug is
not silently recorded as "oracle unavailable". Assert a coverage floor (at least
half of generated sets must reach a comparison) so a refactor cannot turn the
test green by making everything throw.

Setup trap: `createRouteState` does `new Set(["/", ...routes])`, so building the
harness state through it silently adds `"/"` — the exact segment that triggers
one of the two throw classes. Feed both sides the same literal list.

## Using Next as a validator (the salvage)

The invariant is dead, but the idea underneath it is not, and it belongs in the
product rather than the test suite. `getSortedRoutes` is what Next itself uses,
so if it throws on an app's route set, **that app's `next build` will fail.**
`doctor` can call it, catch, and report: _"Next rejects this route set: you
cannot use different slug names for the same dynamic path ('org' !== 'slug')"_ —
early, from the CLI, before the build.

`next` is a peer dependency, so it is present in any consumer's `node_modules`.
Guard the deep import in try/catch and degrade silently when it is missing or
moved. This is a dev-time diagnostic with a graceful fallback, which is the only
context where reaching into framework internals is acceptable. It also covers the
whole class `validateRoutes` structurally cannot see, at the cost of about
fifteen lines.

## Approaches Considered

### Approach A: Static HTML with a hand-written matcher shim (rejected)

Creates a second matcher implementation. Premise 3 rules it out.

### Approach B: `explain()` in core, everything else a thin view (recommended)

`analyzeRoutes` and `explain` in core, composing `matchRouteIn`,
`matchPatternParams`, `compareSpecificity`, `selectQuery`, `normalizePath` and
`validateRoutes`, plus witness synthesis and reject reasons. `doctor` is a
terminal view (v1); the HTML page is a second view over the same functions
(v1.1), with a browser IIFE built from `src/core`.

Effort: v1 ~3 days human / ~2 hrs CC. v1.1 ~3 days human / ~2 hrs CC. Risk: Low.

### Approach C: Hosted playground on top of B (deferred)

"regex101 for Next.js routing" — the same artifact with an empty route list,
working on repos that do not use this library. The strongest distribution story
here, deferred because it is permanent infrastructure on a side project.

## Recommended Approach

**Approach B, split v1 / v1.1.**

Drift is removed structurally: one matcher, compiled twice, verified by one
extracted fixture. The near-miss algorithm gets one home instead of two. And the
engine-first order means v1 ends with `doctor` finding genuinely unreachable
routes from the terminal, validated at zero false positives, before a pixel is
rendered.

## Failure modes

**FM1 — the dangerous drift is against Next, not inside the bundle.** Building
from `src/core` guarantees the HTML agrees with the library, not that the library
agrees with Next. This already ships: the devtools overlay renders a rank derived
from `compareSpecificity`, which disagrees with Next's order.

**Resolved, not deferred: display the library's own rank, labelled `nsr rank`.**
Adopting Next's order would mean replacing `compareSpecificity` with a trie sort,
changing `state.ordered`, `state.staticRoutes`, `getOrderedRoutes()`,
`matchRouteIn`'s candidate order, `getNearestStaticRoute` and `validateRoutes`'s
own sort, and breaking existing assertions in `test/core.test.ts` — a major
version, not a weekend. Labelling the number is honest and costs nothing.

Also unmodeled, and worth an explicit banner: `generate-routes.ts` skips
parallel-route slots (`@slot`) and `route.ts` handlers, so the resolver reports
"no match" for URLs that return 200. `next.config` and middleware rewrites are
not modeled at all. Intercepting routes (`(.)x`) are **not** in this list: they
render an existing URL and contribute no route of their own, so skipping them
loses no URL.

**FM2 — the bundled artifact would be untested.** Nothing currently exercises an
inlined string running as vanilla JS. The repo already has a live instance of the
class: tsup strips `"use client"` and `scripts/add-use-client.mjs` patches it back
after the build. Addressed by the extracted-fixture agreement test (v1.1).

**FM3 — the data goes stale even when the code does not.** Addressed by the stamp.

## Open Questions

1. **How does the CLI carry the browser bundle?** Inline the IIFE as a build-time
   string constant. Reading it from disk breaks on the `./cli` subpath: `cli/index`
   is emitted in CJS as well as ESM, and tsup's default `shims: false` makes
   esbuild rewrite `import.meta` to `{}`, so `import.meta.url` is `undefined` at
   runtime. (`__dirname` is not the hazard — the bin is ESM, where it is simply
   absent.) Inlining makes the question not arise.
2. **`--app-dir` is the default**, because `--out` defaults to
   `route-manifest.ts` and `serializeTs` emits `export const ROUTES = new Set([…])`,
   which a Node CLI cannot import without a TS loader. Accept `--manifest <file>`
   for `.json` only and error clearly on a `.ts` manifest.
3. **Meta in a shareable file:** call the flag `--redact-meta`. It cannot be
   `--no-meta`: `bin.ts` uses one global `parse()` and that name already means
   "skip `route.meta.json`" at generate time.
4. **Size budget:** ≤ 500 KB uncompressed at 500 routes; drop `META` past that.
5. **`stickyQuery` cannot be inlined as plain JSON.** `StickyMatcher` is
   `string | RegExp`, and `JSON.stringify({ stickyQuery: ["locale", /^utm_/] })`
   yields `{"stickyQuery":["locale",{}]}`. Needs a custom encoder (emit `source`
   and `flags`, rebuild with `new RegExp`) plus a test with a regex matcher.
6. **Does `doctor` exit 1 on an unreachable route?** Recommended yes, and keep
   `unreachable` as its own array rather than widening `RouteConflict["kind"]` —
   that union is exported from `src/index.ts`, `src/cli/index.ts` and
   `generate-routes.ts`, and adding a member breaks exhaustive `switch` in
   consumers. `doctor` is additive to `generate --check`, which keeps its current
   errors-only exit behaviour.

  violations in 107,906 conflict-free sets, which is why it was dropped in favour
  of the runtime `doctor` diagnostic.

### Dedup bug: FIXED in this change, not deferred

Originally scoped as its own PR, folded in on request — it is the same
subsystem, and shipping route diagnostics while leaving the largest detection
hole open made no sense.

`walk()` now returns `{ route, dir }` pairs and `collectRoutes` returns a
`sources` map of route to the folders that produced it (additive, non-breaking
on the `./cli` subpath). `generateRoutes` reports any route with two or more
sources as an **error**, naming both folders.

Two subtleties the implementation had to handle:

- `walk()` only inspects SUBdirectories, so a real `app/page.tsx` is invisible to
  it and a root collision (`app/page.tsx` beside `app/(shop)/page.tsx`) would
  have been missed. `collectRoutes` records the root explicitly.
- `"/"` is injected into the manifest whether or not `app/page.tsx` exists. The
  duplicate check runs on walk output only, so the injection can never be
  mistaken for a second source.

Reported under the existing `duplicate` kind rather than a new one, because
`RouteConflict["kind"]` is public and widening it would break an exhaustive
`switch` in a consumer. `level` separates the two cases.

**Behaviour change:** `--check` can now fail a build that previously passed. Any
app it fires on was already failing `next build`, so it moves the failure earlier
rather than creating one.

### Original framing (superseded)

`generate-routes.ts:141` does `[...new Set(["/", ...found])]`, so two route
groups resolving to one path (`(marketing)/about` + `(app)/about`) collapse
before `validateRoutes` sees them. Next hard-fails that at build time, and
`generate --check` structurally cannot detect it. The `duplicate` conflict kind
at `create-router.ts:331-341` iterates the raw iterable so it is not dead code,
but the CLI always feeds it a pre-deduped array. Own PR.
